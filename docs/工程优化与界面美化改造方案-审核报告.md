## 二、与源码不符的事实性描述（必须修订）

### 2.1 ❌ "分型 11 根窗口" 与实际代码不符（重要）

方案第 10 行、第 3.3 节多处声称抽离"分型 11 根窗口""接近分型阈值"。

**实际代码**：
- `filter_fractals_by_extremes(df, window=4)`，其窗口为 `window*2+1 = 9` 根 K 线（非 11）。
- `filter_close_fractals(df, min_gap=4)`，最小索引间隔为 4。
- 涉及"11"的仅剩 `chanlun_processor.py` 的 `if __name__ == "__main__"` 示例数据周期，非业务阈值。

**影响**：方案据此宣称"阈值原值搬入"时依据的数字有误，若照此抽离将抽错值，或与 `window=4` 语义冲突。

**修订建议**：将方案中的"分型 11 根窗口"改为"极值筛选窗口（`window=4`，即 `2*window+1=9` 根）与接近分型最小间隔（`min_gap=4`）"。

### 2.2 ❌ "app/main.py 引用 config.py / utils.py" 的前提不成立（重要）

方案第 3.3 节假设常量"散落在 `app/config.py`"，第 3.5 节假设把"`app/utils.py` 的 `normalize_stock_code`、`get_market_type`"抽到公共包共用。

**实际代码**：
- `app/main.py` **完全未 import** `app/config.py` 与 `app/utils.py`。
- `app/main.py` **内联重定义**了 `normalize_stock_code`、`get_market_type`、`get_previous_workday`、`is_workday`、`get_default_end_date`（约第 32–112 行），与 `app/utils.py`、`mootdx_chanlun.py`、`baostock_chanlun.py` 里的同名函数为**三份重复实现**。
- UI 使用的真实常量（`"600000"`、`datetime(2024,1,1)`、`["mootdx","baostock"]`、`["5","15","30","60"]`、`index=2`、`height=800`）均为 **main.py 内硬编码**，并非来自 `app/config.py`。

**影响**：若照方案"只把 `app/config.py` 的值搬入 `settings.py`"，抽出来的是一份**从未被使用的死配置**，UI 仍是硬编码，无法达到"统一配置"的目标。

**修订建议**：
- 明确重复源为"main.py 内联函数 / CLI 脚本内联函数 / utils.py"三方，抽离后由 `web/app.py` 与 `scripts/*.py` 统一引用。
- `settings.py` 的真实来源应是 **main.py 内的硬编码值 + fetcher 内魔法数字**，而非 `app/config.py`；`app/config.py` 应判定为死代码，纳入清理或迁移清单。

### 2.3 ⚠️ 方案 1.1 备份清单存在笔误

第 24 行 `baostdx_data_fetcher.py` 应为 `baostock_data_fetcher.py`。虽已标注"实际为…"，但建议直接改正，避免 Phase 2 按清单执行时遗漏真实文件。

## 三、设计盲点与风险提示（需澄清）

### 3.1 ⚠️ CLI 脚本"改薄封装"会改变交互行为

方案 3.10 将 `baostock_chanlun.py` / `mootdx_chanlun.py` 改为"薄封装调 `run_analysis`"。

**实际代码**：这两个脚本是**交互式**程序——包含 `input()` 输入循环、`get_user_input`、可视化引擎 fallback（plotly/matplotlib）、HTML 文件保存（`create_and_save_chart`）与 `show_chart` 展示逻辑，并非单纯的"散落编排代码"。

**风险**：直接改薄封装会丢失交互循环与图表展示能力，与方案"功能不增不减"自相矛盾。

**修订建议**：将"CLI 薄封装"明确定义为保留现有交互语义（含输入循环、图表保存/展示），仅把"取数→算法→可视化"的**计算核心**下沉到 `runner`，交互层保留在脚本侧；或单独说明交互式 CLI 是否属本次改造范围，避免隐性删功能。

### 3.2 ⚠️ `run_analysis` 抽象无法完全消除"三处重复编排"

Web 侧 `analyze_stock_with_mootdx` / `analyze_stock_with_baostock` 走 `@st.cache_data` 缓存，且含**数据源 × 市场类型（A股/ETF/指数/港股）× 数据格式**三维分支；CLI 侧各自只有单一数据源、无缓存。

**风险**：一个单一 `run_analysis(code, start, end, source, freq)` 若不能表达"数据源 + 缓存 + 市场类型"三维，则无法真正统一，反而新增一层转发。

**修订建议**：方案应明确 `run_analysis` 的入参范围，或拆分为"数据获取（含市场类型分派）"与"分析 + 可视化"两个可组合函数，并明确**缓存放在哪一层**（建议保留在 web 侧 `@st.cache_data`，CLI 不引入缓存，避免行为漂移）。

### 3.3 ⚠️ `base_fetcher` 抽取未覆盖外部依赖

`mootdx_data_fetcher.py` 在 `__init__` 即初始化最优线路并依赖 `best_server.json` 配置文件；方案 3.6 抽 `base_fetcher` 时未说明该配置文件的迁移/忽略/保留策略。

**修订建议**：在备份与改造说明中明确 `best_server.json` 属**运行时生成**文件（应加入 `.gitignore`），且 fetcher 重构不得改变其读写逻辑。

### 3.4 ⚠️ 算法文件内部"允许动 import/注释"存在边界模糊

方案允许对 `src/core/chanlun_processor.py` "调整文件顶部 import、补充注释"。考虑到该文件自带 `if __name__ == "__main__"` 示例且用相对导入，改动 import 若牵动示例运行路径，可能影响后续手工验证。

**修订建议**：将算法文件的允许操作进一步收敛为"**仅调整 import 行的模块引用路径，不增删 import、不动函数体、不动示例块**"，把任何"补充注释/清理错位注释"列为可选项并逐一 diff 审核。

### 3.5 ⚠️ 一致性验证依赖实盘数据源，建议固化黄金样本

方案 5 节用"同一支股票、同一时段"跑新旧代码对比，但依赖 baostock/mootdx 实盘接口——网络不稳定、线路切换、服务器数据更新都可能导致两侧数据源拿到不同原始数据，从而**误判算法被改**。

**修订建议**：在 Phase 2 先导步骤固化一批**离线黄金样本**（固定股票 + 固定时段 + 保存的原始 K 线 CSV + 期望的分型/笔结果），一致性对比优先跑黄金样本（确定性高），实盘对比作为补充。

## 七、补充审计意见（Phase 1 追加）

> 本节为对原审核报告（二、三、四、五、六节）的**追加补漏**，不推翻既有结论。

### 7.1 ⚠️ 函数重复源不止"三方"——实际至少"五方"，且实现行为有差异（重要）

原报告 2.2/3.2 称"main.py、内联 CLI、utils.py 三方重复"。经全量核查，`normalize_stock_code` / `get_market_type` / `get_previous_workday` / `is_workday` / `get_default_end_date` 至少存在 **5 处副本**，且其中两处实现不完全等价：

| # | 位置 | 是否实现 `get_market_type` | `normalize_stock_code` 关键差异 |
|---|---|---|---|
| 1 | `app/main.py` 第 59-112 行 | ✅ | 完整（ETF `5`/`15`→前缀、港股 `HK`/纯数字、北交所 `8/9/4`） |
| 2 | `app/utils.py` 第 38-122 行 | ✅ | 同上 |
| 3 | `mootdx_chanlun.py` 第 62-94、184-235 行 | ✅ | 同上（但不带"港股代码格式"分支例外提示） |
| 4 | `baostock_chanlun.py` 第 110-148 行 | ❌（**没有** `get_market_type`） | **缺少 `5`→sh ETF、`15`→sz ETF 两条分支**（baostock 历史上不服务 ETF，故该 CLI 隐式不支持 ETF） |
| 5 | `mootdx_data_fetcher.py` 第 329-372 行 | ❌（类内仅有 `_get_market_from_code`，返回 0/1/2 数字） | **完全没有港股分支**，且 ETF/北交所分支均存在 |

**风险**：方案 3.5 抽 `common.py` 时若取任一份"作为模板"统一，**会改变其他入口的行为**（例如把 baostock CLI 的 ETF 支持从"无"补齐为"有"，或 mootdx fetcher 把港股代码当作 A 股处理）。

**修订建议**：
- 明确 **统一基准**为 `app/utils.py` 的实现（最完整），抽到 `src/utils/common.py` 后作为"准绳"。
- `baostock_chanlun.py` 改薄封装时**主动跳过 ETF/港股分支判断**（或加运行时提示"baostock 不支持"），避免误以为它能跑 ETF。
- 把 `MootdxDataFetcher.normalize_stock_code` 替换为调用 `common.normalize_stock_code` 时**补回港股分支**，否则港股代码会在 fetcher 入口就被映射失败。
- 在 Phase 2 验收清单中加一项："5 处调用入口在 ETF/港股/北交所输入下输出一致"。

### 7.2 ⚠️ `app/utils.py` 的 `display_*` / `display_metric` 工具从未被使用（次要）

`app/utils.py` 第 125-148 行定义了 `display_error / display_success / display_info / display_warning / display_metric`，**但 `app/main.py` 全程使用 `st.error / st.success / st.spinner / st.warning` 原生 API，未调用过 `display_*`**。

方案 3.5 提到"抽 `common.py`"，未明示 `display_*` 是否随迁。这部分函数分两种处理：
- **若随迁**：会增加调用点改造工作量（需改 main.py 多处 `st.error(...)` → `display_error(...)`），但风格一致。
- **若删除**：声明废弃即可，不影响功能。

**修订建议**：方案 3.5 增加一行说明——"`app/utils.py` 的 4 个 `display_*` 函数本项目**从未被引用**，迁移到 `src/utils/common.py` 时**删除**即可（保留也仅作 stock 函数，UI 美化阶段不会使用）"。

### 7.3 ⚠️ `BaseFetcher` 抽象接口契约缺失（重要）

方案 3.6 抽 `base_fetcher.py`，但未规定公共接口形态。实际两 fetcher 实现差异巨大：

- `AStockDataFetcher`（baostock）：一次性 `bs.query_history_k_data_plus`，字段重命名后清洗。
- `MootdxDataFetcher`（mootdx）：线路选优 + 按市场类型分流（A股/ETF/港股/指数）+ 分批次 `bars()` + 港股独立服务器列表 + 实时行情等附加 API。

**风险**：Phase 2 抽 base_fetcher 时若仅抽象"取数"这一个动作，会丢掉 mootdx 的多市场分派逻辑；若保留多市场分派，则 base_fetcher 变成 mootdx-only 形态，baostock 无法继承。

**修订建议**：在方案 3.6 增加接口契约草案：
```
# src/data/base_fetcher.py
class BaseFetcher(ABC):
    def fetch_daily(code, start, end, adjustflag='2') -> pd.DataFrame: ...
    def fetch_minute(code, start, end, frequency, adjustflag='2') -> pd.DataFrame: ...
    def fetch_etf(...) / fetch_index(...) / fetch_hk(...) # 由子类按需 override，默认 NotImplementedError
```
明确"取数接口统一 + 多市场扩展由子类各做一份"，避免 base_fetcher 内部又长出 if-elif 链。

### 7.4 🐞 `mootdx_data_fetcher.py` 第 832 行存在明显 IP typo（次要 / 应登记为已知 bug）

`get_hk_stock_data` 的备用港股服务器列表中第 4 项：

```

```

首字符多了一个 `1`，应为 `('124.71.66.200', 7721)`。**这是一个 bug**：当前 IP 永远不会被命中，影响仅限"前 3 个港股服务器都连不上时"的极端情况，但应当登记。

**修订建议**：
- 本方案 Phase 2 **不修改**该 typo（不在"封装/结构/样式"三类之内）。
- 在改造前另开一条 issue，标注为"已知 bug，待 Phase 2 后单独修复"，避免后续追溯不清。

### 7.5 ⚠️ 一致性验证的"黄金样本"缺少存储规范（中等）

审核 3.5 提了"固化离线黄金样本"，方案 5 节对样本的格式、位置、数量、保存方式均未规定。

**补充规范建议**：
- **目录**：`tests/golden_samples/`（与方案目录分层一致，便于 CI 集成）。
- **原始数据**：CSV，列 `datetime,open,high,low,close,volume,amount,code`，文件名 `<source>_<code>_<freq>_<start>_<end>.csv`。
- **期望结果**：JSON，包含 `fractals`（每项含 `index/type/high/low/datetime`）+ `segments`（每项含 `start_idx/end_idx/start_type/end_type/direction/start_price/end_price`），文件名 `<source>_<code>_<freq>_<start>_<end>.expected.json`。
- **样本规模**：至少 3 组——A 股日线（如 `mootdx_sh.600000_daily_2024-01-01_2024-12-31`）、ETF 日线（`mootdx_sh.510300_daily_...`）、跨期切换（`baostock_sh.600519_daily_2020-01-01_2024-12-31`）。
- **比较容差**：分型/笔比较时使用**严格相等**（datetime 字符串相等 + price 用 `math.isclose(rel_tol=1e-9)`），避免浮点误差误判。

### 7.6 ⚠️ `src/utils/logger.py` 的替换范围会大改 fetcher（中等）

方案 3.4 提"替换零散 print 为 `logger.info/warning/error`"，但 `mootdx_data_fetcher.py` 内部有 **30+ 处 `print`**（含线路测试日志、分批进度、错误信息），远超 `chanlun_processor.py` 内的 print 数量。

**风险**：若把"print → logger"作为 fetcher 重构的一部分，工作量接近 fetcher 重构本身，且会改变 CLI 用户的**终端输出样式**（logger 自带时间戳前缀），可能引发"功能漂移"质疑。

**修订建议**：
- 明确 logger 替换仅在以下范围：
  - ✅ `chanlun_processor.py` 内的**业务错误** print（如"输入数据为空"）保持原样不动；
  - ✅ `app/main.py`、`scripts/*.py` 的 print/反馈信息可以替换；
  - ⚠️ `mootdx_data_fetcher.py` **不在本方案 logger 替换范围内**（保留 print），仅在 Phase 2 验收后另立任务。
- 这样方案 3.4 的工作量可控，且**fetcher 行为 100% 不变**。
